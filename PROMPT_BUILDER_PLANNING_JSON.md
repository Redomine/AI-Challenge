# Prompt-builder и сбой JSON на этапе Planning

## Контекст

В рабочем дереве подготовлен этап prompt-builder перед Planning и Direct Execution.
Он использует `GigaChat-3-Ultra` для структурированного понимания запроса.
План строит основная модель (`GigaChat-2-Max` в проверенном окружении).
На момент создания этого документа реализация prompt-builder остаётся
незакоммиченной; эта ветка содержит только отчёт, а не реализацию.

## Наблюдаемая проблема

Проверочный запрос: показать выбранный в Revit 2022 элемент и значение его
параметра `ФОП_ВИС_Имя системы`.

Полный запуск `TaskWorkflow.StartAsync` с реальным prompt-builder и MCP-клиентом
Revit дал следующий результат:

1. Prompt-builder вызвал `GigaChat-3-Ultra` и вернул понимание запроса без
   fallback (`UsedFallback=False`). Он не потребовал ручного ввода ElementId.
2. Planning дважды не смог сформировать разбираемый JSON-план. Последняя ошибка:
   `Planning вернул некорректный JSON: 'A' is an invalid start of a property name.
   Expected a '"'. LineNumber: 11 | BytePositionInLine: 12.`
3. Задача перешла в `PlanningInterrupted`. До согласования плана и вызовов
   Revit-инструментов в этом запуске дело не дошло.

Отдельный запуск консольного агента через `AskAsync` с корректной UTF-8 подачей
того же запроса успешно вызвал `revit_get_selected_elements`, затем
`revit_get_element_parameters` с ID из первого результата и сообщил значение
параметра `ВД`. Это подтверждает цепочку чтения через инструменты, но **не**
проверяет prompt-builder: `AskAsync` обходит `TaskWorkflow`.

Первый консольный тест был недостоверен: PowerShell передал кириллический ввод
как `?`. После явной настройки UTF-8 запрос в истории агента сохранился верно.
Ошибку того запуска нельзя считать сбоем маршрутизации агента.

## Что известно о причине

- API-запрос Planning включает `response_format` с `json_schema` и `strict=true`
  (`DesignerAssistant/Llm/GigaChatClient.cs`). Тем не менее полученный текст
  проверяется `TaskPlanParser`, и он оказался синтаксически неверным.
- При ошибке парсинга исходный текст ответа не сохраняется: преобразование
  происходит до записи в историю (`DesignAssistantAgent.RunStageAsync`).
  Поэтому точное содержимое строки 11 и `finish_reason` не установлены.
- В контракте есть отдельное противоречие: инструкция Planning допускает
  уточнение с пустым `steps`, а `TaskPlanSchema` задаёт `minItems = 1`.
  Это дефект схемы, но связь с данным сбоем не доказана.
- `MaxOutputTokens` по умолчанию равен 1200. Возможное усечение ответа нужно
  проверять по фактическому `finish_reason`, а не предполагать.

Следовательно, непосредственный сбой произошёл на границе ответа основной
модели и парсера плана. Данных, чтобы обвинить Ultra или назвать единственную
причину некорректного JSON, пока недостаточно.

## Варианты решения

### A. Диагностика и исправление контракта (рекомендуемый первый шаг)

- При неуспешном Planning сохранять локально диагностический артефакт:
  исходный ответ модели, `finish_reason`, имя модели, число выходных токенов,
  ошибку синтаксической и семантической проверки. Исключить ключи авторизации
  и не публиковать данные проекта.
- Согласовать инструкцию, JSON-схему и валидатор для двух случаев:
  непустой план без уточнения и уточнение с пустым списком шагов.
- Повторить один запрос 10-20 раз и классифицировать сбои: усечение, неверный
  JSON, неверная структура, неизвестный инструмент или отсутствие аргументов.

Плюс: минимальный объём изменений и проверяемая причина. Минус: сам по себе
этот шаг не гарантирует устойчивости генерации.

### B. Усиление Planning

- Уменьшить объём передаваемого каталога инструментов до релевантных запросу,
  сохраняя обязательные Revit-инструменты и их реальные схемы.
- Разделить повторы по типу ошибки: при `finish_reason`, указывающем на
  ограничение длины, увеличить допустимый вывод; при ошибке JSON запросить
  новый структурированный ответ; при ошибке валидации передать точное
  замечание валидатора.
- Не извлекать значения аргументов из недостоверного текста и никогда не
  исполнять план до успешной проверки схемы, доступности инструментов и
  источников обязательных аргументов.

Плюс: выше шанс завершить сложный запрос. Минус: дополнительные вызовы модели
и стоимость; нужны ограничение числа попыток и диагностика каждого повтора.

### C. Отдельный детерминированный маршрут для частых Revit-запросов

Для однозначного запроса о текущем выделении локально начинать с
`revit_get_selected_elements`, затем передавать фактический результат в
`revit_get_element_parameters`. Prompt-builder может уточнять намерение, но
не должен заменять инструментальные факты. Для сложных запросов сохранять
общий Planning.

Плюс: простой read-only сценарий меньше зависит от формата LLM-плана.
Минус: маршрут должен быть узким; нельзя превращать его в набор специальных
правил под каждый запрос. Сверять с существующими правилами `ToolRouter`.

## План проверки

1. Модульные тесты: валидный план, уточнение без шагов, ошибочный JSON,
   усечённый ответ, ошибка инструмента, два неудачных повтора. Проверить,
   что исполнение не начинается после сбоя Planning.
2. Контрактный тест реального GigaChat: запросить структурированный план,
   проверить JSON и схему, сохранить диагностические данные только локально.
3. Сквозной read-only тест на Revit 2022 через `TaskWorkflow`: Ultra, Planning,
   согласование, `revit_get_selected_elements`, затем
   `revit_get_element_parameters` с фактическим ID, валидация и итоговый ответ.
   Отдельно проверить пустое выделение и отсутствующий параметр.
4. Повторить сценарий 10-20 раз без ручного ввода ElementId. Успех означает:
   ни одного изменения модели, точное значение из MCP-ответа, корректное
   завершение workflow и сохранённую причину каждого неуспеха.

После изменений в маршрутизации или многошаговом исполнении запускать полный
`DesignerAssistant.Tests`, пересобирать и перезапускать `DesignerAssistant.Web`,
затем проверять прослушиваемый порт согласно `AGENTS.md`.

## Приоритет

Начать с варианта A и повторного живого теста. По полученным сырым ответам
выбрать нужную часть варианта B. Вариант C рассматривать только если частый
сценарий выделения продолжит срываться на Planning и его можно ограничить
без разрастания специальных правил.
