# День 11. Память помощника BIM-координатора

## Цель

Перевести приложение с роли «Помощник проектировщика» на роль персонального
технического помощника BIM-координатора. Агент должен помогать пользователю с
саппортом, диагностикой и тестированием моделей, плагинов и скриптов, вести
диалог через GigaChat, хранить три явно разделённых слоя памяти и получать
актуальные данные открытой модели через `rvt-mcp`, не подменяя результаты Revit
предположениями модели.

Первая версия работает только на чтение. Изменения модели включаются отдельным
этапом после проверки сценариев чтения и всегда требуют подтверждения человека.

## Архитектура

```text
Пользователь
    |
    v
BIM Coordinator Agent (.NET 8)
    |-- GigaChat: рассуждение, выбор инструмента, итоговый ответ
    |-- IMemoryStore: short-term / working / long-term
    `-- IMcpClient: MCP stdio
            |
            v
        rvt-mcp 0.6.1
            |
            +-- TCP localhost -> Revit 2022 plugin -> Revit API
            `-- TCP localhost -> Revit 2024 plugin -> Revit API
```

`rvt-mcp` установлен локально и зарегистрирован в Codex в безопасном режиме:

```toml
[mcp_servers.rvt-mcp]
enabled = true
command = 'C:\Users\Mankaev_r\AppData\Local\RvtMcp\rvt\server\0.6.1\rvt-mcp.exe'
args = ["--read-only", "--disable-toolbaker"]
```

Наше приложение использует отдельный MCP-клиент с теми же аргументами. Оно не
зависит от конфигурации Codex и не вызывает `rvt-mcp` через оболочку.

## Роль агента

Помощник BIM-координатора:

- помогает разбирать обращения пользователей и воспроизводить проблемы;
- анализирует состав, параметры и состояние BIM-модели;
- проверяет активный документ, вид, выборку и рабочие наборы;
- помогает тестировать плагины, pyRevit-скрипты и сценарии работы с моделью;
- фиксирует тестовую среду, шаги воспроизведения, ожидаемое и фактическое
  поведение;
- сопоставляет факты из Revit, журналы и наблюдения с условиями текущей задачи;
- помогает локализовать причину проблемы, не выдавая гипотезу за подтверждённый
  результат;
- готовит краткий технический отчёт с идентификаторами элементов, версией Revit
  и источником каждого факта;
- не утверждает, что видел или изменил модель, без успешного результата MCP;
- не выполняет изменение модели без явного подтверждения пользователя.

## Слои памяти

| Слой | Данные BIM-координатора | Срок жизни | Хранилище |
|---|---|---|---|
| Краткосрочная | Последние реплики, последние результаты MCP и уточнения | Текущий диалог | `short_term_messages` |
| Рабочая | Текущее обращение или тест: среда, версия плагина, шаги воспроизведения, ожидаемое и фактическое поведение, целевой Revit, документ, вид, выборка и гипотезы | До завершения задачи | `working_memory` |
| Долговременная | Профиль пользователя, стандарты компании, особенности поддерживаемых версий Revit, известные плагины, подтверждённые решения и формат отчёта | Между сессиями | `long_term_memory` |

Данные разных слоёв хранятся отдельно. Ответ MCP не записывается автоматически в
долговременную память.

## Модели данных

```csharp
public enum MemoryLayer
{
    ShortTerm,
    Working,
    LongTerm
}

public enum MemorySource
{
    User,
    RevitMcp,
    Agent
}

public enum EvidenceStatus
{
    Reported,
    Observed,
    Hypothesis,
    Confirmed
}

public sealed record MemoryEntry(
    long Id,
    MemoryLayer Layer,
    string Key,
    string Value,
    MemorySource Source,
    EvidenceStatus Status,
    string? TaskId,
    DateTimeOffset CreatedAt,
    DateTimeOffset UpdatedAt);

public sealed record RevitTarget(
    int Year,
    int ProcessId,
    string? DocumentIdentity,
    string? DocumentTitle);
```

`ChatMessage` остаётся только единицей диалога. Структурированная память не
хранится в тексте сообщений.

`DocumentIdentity` должен строиться из устойчивых доступных признаков документа,
а не только из заголовка окна. Результаты, содержащие `ElementId`, всегда
связываются с документом, версией Revit и текущей задачей.

## Ограничения хранения Revit-данных

1. `ElementId`, активный вид, выборка и PID процесса хранятся только в рабочей
   памяти.
2. Перед повторным использованием `ElementId` агент проверяет целевой процесс и
   идентичность документа через MCP.
3. Закрытие или смена документа делает сохранённые идентификаторы элементов
   неактуальными и очищает соответствующий рабочий контекст.
4. Результаты MCP получают `Source = RevitMcp` и время чтения.
5. Вывод GigaChat не становится фактом Revit без подтверждающего MCP-вызова.
6. В долговременную память не записываются пути моделей, параметры элементов и
   содержимое проекта без явного решения пользователя.
7. Причина сбоя остаётся `Hypothesis`, пока её не подтвердил повторяемый тест,
   журнал, результат MCP или пользователь.

## Явная запись в память

1. Каждая успешная пара `user/assistant` сохраняется только в краткосрочную
   память.
2. `/remember work <key> <value>` записывает условие текущего обращения или
   теста в рабочую память: окружение, шаг, наблюдение, ожидание или гипотезу с
   явно указанным статусом.
3. `/remember long <key> <value>` записывает подтверждённое постоянное правило.
4. Результат MCP сохраняется в рабочую память только тогда, когда он нужен для
   следующих шагов текущей задачи.
5. `/task complete` удаляет рабочую память задачи, включая `ElementId`.
6. `/clear` очищает только краткосрочную память.
7. `/memory` показывает слой, источник, задачу и время обновления записи.

Автоматически извлечённый GigaChat факт можно показать как предложение, но нельзя
сохранять в долговременную память без явного подтверждения пользователя.

## Команды BIM-координатора

```text
/revit select                  показать полные имена сеансов и ID
/revit select <ID|имя>         выбрать конкретный сеанс
/revit status                  показать процесс, документ и активный вид
/revit selection               прочитать выбранные элементы
/memory                        показать три слоя памяти
/history                       показать восстановленный диалог
/help                          показать все доступные команды
/remember work <key> <value>   сохранить условие текущей задачи
/remember long <key> <value>   сохранить постоянное правило
/clear                         очистить текущий диалог
/task complete                 завершить задачу и очистить рабочую память
```

После перезапуска приложение загружает сохранённые сообщения текущего диалога из
SQLite и выводит их в консоль до первого приглашения ввода. Команда `/history`
повторно показывает восстановленный диалог. Напоминание `/help — команды`
присутствует в каждом приглашении ввода, а `/help` перечисляет только реально
реализованные команды.

Если одновременно запущены Revit 2022 и 2024, агент не выбирает цель молча. До
первого модельного запроса он вызывает `revit_list_available_targets` и просит
выбрать версию либо использует уже явно сохранённую цель текущей задачи.

## Сборка контекста GigaChat

Перед ответом агент формирует контекст в следующем порядке:

1. системная инструкция помощника BIM-координатора;
2. разрешённые MCP-инструменты и правила их применения;
3. долговременная память;
4. рабочая память текущей задачи;
5. последние N сообщений краткосрочной памяти;
6. новый вопрос пользователя.

Рабочая память имеет приоритет над долговременной. Свежий успешный результат MCP
имеет приоритет над сохранённым рабочим значением. Конфликт показывается
пользователю, а не разрешается скрыто.

Диагностический режим выводит `Memory context` и `Tool trace`: выбранные записи,
имя MCP-инструмента, целевой Revit, аргументы без секретов, длительность и статус.
Токен discovery-файла, ключ GigaChat и полная системная инструкция не выводятся.

## Проверка через GigaChat и живой Revit

Проверка выполняется на тестовой модели, не на рабочей центральной модели. Revit
2022 и Revit 2024 запускаются одновременно, чтобы проверить явную маршрутизацию.

### Сценарий

```text
/remember long report_style краткий список с ElementId
/revit select
/revit select <ID>
/revit status
/revit selection
Что выбрано, какие параметры доступны и достаточно ли данных для воспроизведения проблемы?
/clear
Какой формат отчёта нужно использовать?
/task complete
/memory
```

### Проверяемые результаты

1. `/revit select` возвращает полные имена сеансов и разные PID.
2. После `/revit select <ID>` запросы не уходят в другой Revit.
3. Выбранные `ElementId` появляются только в рабочей памяти и содержат привязку
   к документу и версии Revit.
4. Ответ GigaChat ссылается только на факты, реально возвращённые MCP.
5. После `/clear` исчезает история диалога, но цель задачи и формат отчёта
   остаются.
6. После `/task complete` удаляются цель Revit, документ, выборка и `ElementId`,
   а долговременный формат отчёта сохраняется.
7. При переключении документа старые `ElementId` отклоняются как неактуальные.
8. В `read-only` отсутствуют `revit_send_code_to_revit`, create/modify/delete и
   попытка GigaChat вызвать их блокируется приложением.
9. `Tool trace` показывает реальную версию Revit и статус каждого вызова.
10. Один вопрос повторяется с заполненной памятью и после очистки каждого слоя;
    в отчёте сравниваются контекст, ответ GigaChat и расход токенов.

## Следующий этап: массовая проверка инженерных элементов

### Цель и границы первой версии

Помощник запускает проверку всей активной модели из диалога, в том числе со
стартового экрана помощника; для проверки активный вид не требуется.
Элементы связанных моделей не учитываются. Проверка только читает модель и не
открывает, не выделяет и не меняет элементы. Ответ GigaChat строится по
агрегированным результатам; формат ответа определяется запросом пользователя.

Набор категорий по умолчанию:

```csharp
BuiltInCategory.OST_DuctFitting,
BuiltInCategory.OST_PipeFitting,
BuiltInCategory.OST_PipeCurves,
BuiltInCategory.OST_DuctCurves,
BuiltInCategory.OST_FlexDuctCurves,
BuiltInCategory.OST_FlexPipeCurves,
BuiltInCategory.OST_DuctTerminal,
BuiltInCategory.OST_DuctAccessory,
BuiltInCategory.OST_PipeAccessory,
BuiltInCategory.OST_MechanicalEquipment,
BuiltInCategory.OST_DuctInsulations,
BuiltInCategory.OST_PipeInsulations,
BuiltInCategory.OST_PlumbingFixtures,
BuiltInCategory.OST_Sprinklers,
BuiltInCategory.OST_CableTray
```

Для запроса вне этого списка нужен отдельный инструмент выбора произвольных
категорий, например систем воздуховодов и систем трубопроводов. Категории
идентифицируются по `BuiltInCategory`, а не по русскому имени. Каталог
русских синонимов помогает распознать запрос; отображаемое имя берётся из
Revit через `LabelUtils.GetLabelFor(BuiltInCategory)` и проверяется в Revit
2022/2024. Отсутствующая в документе категория даёт нулевой счётчик, а
не ошибку.

### Контракт выборок и проверок

1. Инструмент сбора создаёт серверную выборку экземпляров и возвращает только
   непрозрачный `selectionId`, идентичность документа, время чтения, общее
   количество и счётчики по категориям. Полный список `ElementId` не
   возвращается модели.
2. Инструмент проверки принимает `selectionId` и структурированные условия
   по одному или нескольким параметрам экземпляра и/или типа. Он создаёт
   новую выборку из подошедших элементов, сохраняя ссылку на исходную.
   Последовательное сужение поддерживается сразу; идентификаторы выборок и
   происхождение результата проектируются так, чтобы позднее добавить
   объединение независимых выборок.
3. Поддерживаются как минимум `NullOrEmpty`, `Equals`, `NotEquals` и проверки
   наличия параметра. Для строк `null` и `""` входят в один результат
   `NullOrEmpty`; отсутствие параметра выводится отдельной группой. Числовой
   `0` является заполненным значением и проверяется через равенство/неравенство.
   Значения из пробелов не объединяются с `NullOrEmpty`; их поведение
   проверяется на живом Revit и фиксируется в контракте.
4. Если имя параметра совпадает у нескольких определений, инструмент не
   выбирает одно молча: возвращает неоднозначность с доступными признаками
   определения (источник экземпляр/тип, GUID при наличии, другие устойчивые
   идентификаторы). Пользовательский запрос можно уточнить и повторить.
5. Выборка привязана к целевому процессу, документу и текущей задаче.
   Перед повторным использованием проверяются процесс и идентичность
   документа. При смене документа, завершении задачи или истечении срока
   хранения выборка становится недействительной. `selectionId` не является
   долговременной памятью.
6. Для каждого прогона возвращаются счётчики: исходное количество, подошло,
   не подошло, параметр отсутствует, неоднозначный параметр, ошибки чтения;
   распределение по категориям и значениям только в ограниченном размере.
   Частичный результат обозначается явно и не выдаётся за полную проверку.

Пример цепочки: собрать категории по умолчанию -> оставить элементы, где
`Имя системы != "Не определено"` -> среди них оставить элементы, где
`ФОП_ВИС_Имя системы принудительное` не `NullOrEmpty` -> получить сводку.
Выход каждого шага передаётся следующему как фактический `selectionId`.

### Отчёты и бюджет контекста

- Полный результат хранится локально вне диалога. Отдельная папка отчётов
  группирует файлы по задаче; её точный путь задаётся конфигурацией и
  валидируется как разрешённый локальный каталог. Экспорт выполняется
  отдельным явным действием, когда отчёт нужен пользователю.
- JSON-отчёт содержит метаданные проверки, `ElementId`, категорию и только
  проверяемые параметры с признаками источника и определения. Имя документа,
  путь и служебные данные не попадают в запись каждого элемента. Экспорт
  возвращает путь, количество записей, размер и SHA-256, но не содержимое.
- Для просмотра доступна ограниченная страница элементов со стабильной
  сортировкой. Максимальный размер страницы и ответа зафиксирован в схеме;
  запрос без лимита отклоняется или получает безопасный лимит по умолчанию.
- JSON является основным форматом хранения. TOON формируется только из
  компактной сводки или запрошенной страницы перед передачей GigaChat.
  Полный JSON не сериализуется в prompt, историю сообщений или память.
  Если TOON-кодек недоступен либо не даёт выигрыша, передаётся ограниченный
  структурированный JSON с тем же бюджетом контекста.
- В рабочей памяти остаются ссылка на выборку, краткая сводка и статус
  отчёта. При `/task complete` выборки очищаются; сохранённый файл отчёта
  управляется отдельно и не удаляется неявно.

### Инструменты и размещение кода

Планируемые операции: сбор по категориям по умолчанию, отдельный сбор по
явно указанным категориям, фильтрация выборки, получение сводки, получение
страницы и экспорт JSON. Названия MCP-методов и схемы аргументов закрепить
в документации до реализации. Каждый инструмент имеет узкую read-only
классификацию и ограниченный ответ.

В `rvt-mcp-custom` соблюдать локальные `AGENTS.md` и `CUSTOM_TOOLS.md`:
описания в `docs/custom-tools/`, MCP-объявления в `src/server/CustomTools/`,
Revit-обработчики и DTO в `src/shared/CustomTools/`, тесты в
`tests/RvtMcp.Tests/CustomTools/`. Исходные upstream-файлы менять только
для разрешённой регистрации. Для ID применять `RevitCompat.GetId()` и
`RevitCompat.ToElementId()` согласно локальному `AGENTS.md` этого репозитория.

В текущей конфигурации `custom` включает и инструменты записи, поэтому
`--read-only` скрывает весь toolset. Перед подключением проверить фактическую
классификацию и `tools/list`; в помощнике новые методы разрешить только
явным allowlist и read-only policy. Не расширять доступ к произвольному коду.

В `AI_Challenge` после стабилизации контракта обновить клиентский allowlist,
ручной русский каталог возможностей, маршрутизацию и многошаговый вызов.
Агент должен использовать реальные `selectionId` из ответов MCP и
останавливаться на ошибке, устаревшей выборке или неоднозначном параметре.

### Делегация GigaCode Ultra и порядок работ

GigaCode Ultra получает одну ограниченную задачу за раз, с путями разрешённых
файлов, контрактом, примерами входа/выхода и критериями приёмки. Он пишет
код и тесты в `rvt-mcp-custom`; Codex проверяет diff, контракт, границы
репозитория и результаты тестов. Секреты GigaChat и данные рабочих моделей
не включаются в задания. Ни один этап не считается принятым только по
текстовому отчёту агента.

1. **Спецификация.** Сверить русские имена категорий по документации Autodesk
   и на живых Revit 2022/2024; описать схемы, лимиты, ошибки, жизненный
   цикл выборок и папку отчётов. Результат: документы инструментов и
   контрактные примеры без реализации.
2. **Сбор.** Поручить Ultra серверную выборку для 15 категорий, затем
   отдельный инструмент произвольных категорий. Принять после тестов
   пустой модели, отсутствующей категории и большой модели.
3. **Параметры.** Поручить Ultra фильтрацию экземпляров и типов,
   `NullOrEmpty`, числовые сравнения, отсутствие и неоднозначность параметра.
   Принять после теста цепочки из двух условий с фактическим `selectionId`.
4. **Результат.** Поручить Ultra агрегаты, ограниченную страницу и JSON-экспорт.
   Проверить, что ни один обычный ответ MCP не содержит полного списка ID,
   а файл содержит только поля контракта.
5. **Интеграция помощника.** Подключить схемы к allowlist, каталогу и
   agent loop; преобразовывать ограниченные данные в TOON у границы
   GigaChat. Добавить сквозные тесты естественных запросов, включая
   отрицательные случаи и последовательное сужение.
6. **Живая приёмка.** Собрать сервер и плагины, проверить новую установленную
   версию, `tools/list` и реальные вызовы в тестовых моделях Revit 2022 и
   2024. Проверить стартовый экран, смену документа, десятки тысяч элементов,
   время, память и размер контекста; сверить выборочные результаты вручную.

Для каждого этапа Codex фиксирует: изменённые файлы, diff-аудит,
компиляцию, релевантные и полные тесты, живую проверку отдельно от .NET
тестов и оставшиеся ограничения. До готовности предыдущего контракта
Ultra не получает следующий этап. Коммиты, push и публикация выполняются
только по отдельному запросу пользователя.
